# ADR 0003: Single-user authentication

Status: accepted; production CPU telemetry remains pending an authorized deployment.

## Decision

Use native Worker WebCrypto PBKDF2-SHA256, 100,000 iterations (the production
maximum), 128-bit random
salt, 256-bit output. Bootstrap username and precomputed password hash come only
from secrets. `cargo xtask auth-hash` reads a password from stdin and generates the
compatible format. First successful login upserts the only allowed user (id 1).
Secret changes control future logins; they do not implicitly revoke active sessions.
There is no registration, invitation, or user management UI.

Use constant-time byte comparisons (`subtle`) for password digests and usernames.
Keep PBKDF2 in WebCrypto rather than a synchronous wasm loop. The secret parser
rejects unknown algorithms, malformed/noncanonical counts, zero, counts above
100,000, and invalid salt/digest sizes. Verification uses the count stored in each
hash (1 through 100,000). Raising the default and maximum later will preserve
verification of existing hashes.

## Measurement and free-tier tradeoff

Measured on this development host with `cargo run --release -p xtask -- auth-bench`:

| Algorithm | Three release runs |
| --- | --- |
| RustCrypto Argon2id, 19,456 KiB, t=2, p=1 | 31.37, 27.67, 21.67 ms |
| RustCrypto PBKDF2-SHA256, 600,000 | 78.70, 78.05, 77.63 ms |

Even native Argon2 exceeds the 10 ms free-tier CPU budget, before wasm overhead.
This rules out synchronous RustCrypto hashing for this Worker. Native PBKDF2 is
also unsuitable; the deployed implementation delegates to asynchronous WebCrypto.
Historical local `wrangler dev` integration at 600,000 iterations measured the full login at about 108 ms wall time;
subsequent login requests were about 80–86 ms in Wrangler logs. This includes native
crypto and D1 work, not just wasm execution. A host benchmark and local wall time
cannot establish Cloudflare's production CPU accounting. No production deployment
was authorized, so this ADR does **not** claim verified compliance with 10 ms.
Check production CPU telemetry during an explicitly authorized deployment; if native
crypto is charged above the allowance, revisit hosting/budget rather than weaken
PBKDF2 iterations. Keep the benchmark reproducible in xtask.

## Sessions, tokens and request boundary

Generate 32 random bytes with Worker crypto for each session and API token.
Encode as hex (API tokens prepend `tk_`), persist only SHA-256 digests. High-entropy
random credentials need a fast hash, unlike passwords. Session lookups enforce
expiry in SQL; bearer lookups atomically reject revoked tokens and update last use.
Metadata list queries never select hashes. Token revocation takes effect on the next
lookup; a request already authenticated can finish.

Session lifetime is seven days. Cookie: HttpOnly, Secure, SameSite=Lax, Path=/.
Logout deletes the session and expires the cookie. State-changing cookie requests,
including login, require Origin equal to the request URL origin. Bearer credentials
are explicit and do not require Origin; invalid Authorization never falls back to
cookies. All private API routing passes through one auth gate before dispatch.
Health and login are the only public API handlers. Auth responses disable caching.

Persist a fixed-window D1 rate counter keyed by the SHA-256 of the Cloudflare
source IP: five login attempts per 15 minutes, checked before password derivation.
Successful attempts count too. Expired counters are pruned on subsequent login.
The local fallback key is shared when the Cloudflare IP header is absent. This is
basic brute-force protection, not distributed abuse protection or an account lock.

## Verification

Core tests cover digest hashing, constant-time equality, credential parsing, password
vectors (cross-checked with OpenSSL), expiry boundaries and revoked rejection.
SQLite tests exercise the exact session and bearer statements used by D1.
`cargo xtask auth-verify` exercises a running localhost Worker using an ignored
`target/login.local` JSON fixture; all cookies and credentials stay under target.
It checks cookie flags, login, Origin rejection, private routing, last use, metadata,
revocation, logout and rate limits. Reset only the local login_attempts table before
rerunning within 15 minutes. This command creates ignored browser storage for a
metadata-only screenshot. Never capture the one-time raw token in committed images.

The updated 100,000-iteration local integration passed with a 43.29 ms full-login
wall time. This is not a production CPU measurement.

## Accepted runtime tradeoff and residual risk

The lead chose WebCrypto PBKDF2-SHA256 at the production runtime maximum of
100,000 iterations. This resolves the runtime compatibility decision. Historical
600,000-iteration host measurements above remain comparison data only.

OWASP recommends 600,000 PBKDF2-HMAC-SHA256 iterations for password storage to
resist offline guessing after database leaks, including user-chosen passwords.
This single-user app accepts a lower work factor because Calum sets a generated
passphrase via a Worker secret. This is an application-specific exception, not
an OWASP-equivalent configuration.

`cargo xtask auth-hash` refuses passwords shorter than 16 Unicode characters.
Use a generated passphrase: length alone does not guarantee entropy. The hash
lives only in the Worker secret `BOOTSTRAP_PASSWORD_HASH`, never in the repository
or D1 dumps. Login retains constant-time comparisons and five attempts per IP per
15 minutes. Migration 0004 drops the unused `users.password_hash` column, so D1
holds no password material.

If the Worker secret leaks, attackers can guess offline and bypass rate limits.
100,000 iterations give roughly six times less per-guess work than 600,000.
Weak/reused passwords remain vulnerable, and distributed online guessing can
bypass per-IP limits. Secret access and generated passphrase entropy are material
controls, not guarantees. Production CPU accounting remains unmeasured: inspect
telemetry during an explicitly authorized deployment. No deployment is authorized
by this decision.
